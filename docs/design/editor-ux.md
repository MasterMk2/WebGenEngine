# 管理画面とエディタの UX（v0 検討）

- 状態: 検討。2026-10-29
- §2 の「現状」は、試作（`packages/editor/`）を実際に操作して数えた事実
- §3 以降の提案は、まだ描画も操作もしていない。手数は設計上の見込み。例外は次の 3 つで、試作して確かめた
  - §3.2 の直接編集
  - §3.1 の選んだ部品のツールバーと、§4.2 の挿入点（§3.8）
  - §3.3 の自動保存・公開・履歴（§3.8）
- 目的: 保存先の API や部品の形式を作る前に、それらの形を左右する UI の判断を先に決める

## 0. 結論

1. **プレビューの文字をクリックしたら、その場で書けるようにする。** 利用者がいちばん多く行うのは、既存ページの文字や画像の差し替え（営業時間、お知らせなど）。いまは手数が 4 で、目線もプレビューから右の欄まで移る。直接書く方式なら 1〜2 で済む（§3.1）
2. **ソースは既定で隠し、ボタン 1 つで出す。** 双方向（D2）は保ったまま、R2（専門用語を出さない）を守る（§3.6）
3. **部品の追加は、`区画・並び・格子` を組み立てる方式から、パターン（できあがったまとまり）を選ぶ方式に変える。** 並びや格子は、選んだあとに「横に並べる」「列の数」として変える（§3.4、§3.5）
4. **自動保存、下書き、公開、版の履歴を分ける。** これが保存 API の形を決めるので、API より先に決める（§3.3）
5. 次の 4 つは利用者に決めてもらう（§8）
   - 操作のしかた
   - ソースを既定で表示するか
   - スマートフォンでどこまで編集できるか
   - パターンを R1 の部品と同じものにするか

## 1. 前提

- 画面の種類: 道具（作業画面）。主役は編集しているページそのもの
- 主な利用者: 個人・中小企業の担当者（D9）。HTML の知識はない。PC が中心だが、スマートフォンから急ぎで直したい場面もある（仮定）
- 副の利用者: 制作会社やエンジニア。ソースを読み書きする
- 主なタスク（頻度 × 重要度の順。仮定）

| # | タスク | 頻度 | 備考 |
|---|---|---|---|
| T1 | 既存のページの文字や画像を差し替える | 毎週 | 営業時間、価格、写真 |
| T2 | 記事（お知らせ・ブログ）を書いて公開する | 毎週 | 文章が中心 |
| T3 | 公開する／公開を取り消す・前の版に戻す | T1・T2 のたび | R2「どの操作も取り消せる」 |
| T4 | ページにまとまり（お知らせ一覧、アクセス、料金表）を足す・並べ替える | 月に数回 | |
| T5 | 初回に、トップページと記事 1 件を公開する | 1 回 | R2 の受け入れ基準（30 分） |

## 2. 現状の試作で観察したこと（2026-10-29、アプリ内のブラウザ、1440×900 と 375×812）

手数は「クリック・キー操作の回数＋文字入力」で数えた。

| タスク | マウスでの手数 | 観察したこと |
|---|---|---|
| T1 見出しの文字を変える | 4＋入力 | 部品をクリック → 右の「文字」の欄をクリック → 既存の文字を選ぶ → 入力 → 欄の外へ出る。**入力中はプレビューが変わらず、欄から出たとき（`change`）に初めて反映される**。目線はプレビューから右の欄まで約 700px 動く |
| T1 太字を含む文を変える | GUI ではできない | 「ソースで直す」と案内される（editor.md §1） |
| T4 文章を 1 つ足す | 5＋入力 | 基準の部品を選ぶ → ツールバーの「＋文章」→ 右の欄で「文章を入れてください。」を選んで消す → 入力 → 欄の外へ。**どこに入るかは押すまで分からない**（選んだ箱の末尾か、選んだ部品の直後か、ページの末尾） |
| T4 まとまりを足す | 10 以上 | 「＋区画」「＋並び」「＋格子」を組み合わせる。並びや格子の考え方を知らないと作れない |
| T3 公開 | できない | 保存先はブラウザの localStorage だけ |

ほかに気づいたこと:

- 専門用語がそのまま出ている（R2 に反する）。右の欄の見出しは `<Heading>`、属性名は `level`・`align`、選択肢は「中央 (center)」「先頭側 (start)」
- 部品の呼び名が作る側の言葉になっている。「区画」「並び」「格子」は、利用者が頭の中で使う言葉ではない（仮定。ユーザーテストで確かめる）
- ソースが常に画面の半分近くを占めている
- 「サンプルに戻す」は試作用の操作。製品の画面には要らない
- スマートフォン幅（375px）では、ツールバーの「＋区画」などが 1 文字ずつ折り返して縦長になる。設定の欄は画面下に回り、プレビューが狭くなる
- キーボードでは、プレビューの部品を選べない。ソースのカーソルを動かすしかない
- 計測スクリプト（ui-audit.js）の結果
  - 名前のないボタン、ラベルのない入力欄、横のはみ出しは 0 件
  - 11px の文字が 3 件（属性名の `code`）
  - 押し領域は 20 個中 18 個が 44px 未満。PC では問題ないが、指で触る場合は小さい
  - 塗りの強いボタンが 0 個。画面の主な操作（のちの「公開」）がまだない
  - コントラストの警告が 2 件出た。ソースの欄の色付け用の下敷き（透明な文字）を数えたもので、実際の問題ではない

## 3. いま決めること（あとから変えると高くつくもの）

### 3.1 操作のしかた（直接編集）

最も多いタスク T1 で、2 つの案の手数を比べた。

- **案 A（そのまま書く）**: 文字の部品はクリックした位置にすぐカーソルが立つ。移動は、選んだときに出る小さなツールバーの取っ手（⠿）で行う。WordPress のブロックエディタや Notion に近い
- **案 B（選んでから書く）**: 1 回目のクリックで選び、ダブルクリックか Enter で書き始める。移動は部品のどこを掴んでもよい。Keynote や Figma に近い

| 入力の手段 | 現状 | 案 A | 案 B |
|---|---|---|---|
| マウス: 文字の差し替え | 4＋入力 | 1＋入力（終えるときの外のクリックは、次の操作を兼ねる） | 2＋入力 |
| マウス: 並べ替え | 1〜2（親を選ぶ＋ドラッグ） | 1〜2（親を選ぶ＋取っ手） | 1〜2 |
| タッチ: 文字の差し替え | 未確認（プレビューをタッチでスクロールできないので、画面外の部品には届かない） | 1＋入力＋「完了」 | 2＋入力（ダブルタップは拡大と衝突する） |
| キーボード: 文字の差し替え | ソースを直接書くしかない | ↑↓で部品を選ぶ → Enter → 入力 → Esc | 同じ |

**推奨は案 A。** 文字の差し替えは並べ替えよりずっと多く、案 A なら 1 手少ない。そのかわり、文字の上でドラッグすると文字の範囲選択になるので、移動は取っ手からに限る。画像や箱は、クリックで選び、そのままドラッグで動かせる（いまの試作と同じ）。

選んだ部品のすぐ上に、次の操作を並べた小さなツールバーを出す。操作を対象のそばに置き、右の欄まで目線を動かさないようにする。

```
[⠿] セクション › 並び › カード › 見出し ▾ | B  I  リンク | ↑ ↓ | ＋ | …
 取っ手  親をたどる道筋（クリックで親を選ぶ）     文字の書式        移動    追加  複製・削除など
```

- 道筋は、いまの「親を選ぶ」の代わり。何段上を選んでいるかが見える
- 太字とリンクは、選んだ文字の範囲に付ける（Ctrl+B、Ctrl+K）。いまは GUI で直せない、太字を含む文も直せるようになる
- 削除は確認なしで行い、「元に戻す」を併記した知らせを出す。知らせが消えても、Ctrl+Z とツールバーの「元に戻す」で戻せる

### 3.2 直接編集をどう作るか（未解決）

いまのプレビューは、スクリプトが動かない iframe（`sandbox="allow-same-origin"`）の上に透明な層を重ね、クリックをすべて層で受けている（editor.md §4）。案 A はこの作りとぶつかる。候補は 2 つ。

| | 方式 1: 親の画面に編集欄を重ねる | 方式 2: iframe の中の要素を直接編集できるようにする |
|---|---|---|
| 作り | 選んだ要素の位置と文字の形を写した編集欄を、透明な層の上に重ねる | 編集中の要素だけ `contenteditable` にし、入力は親の画面で受ける（`allow-same-origin` なので親から DOM に触れる） |
| 良い点 | iframe の作りを変えない | 実物の表示のまま書ける。行の折り返しも、下の要素がずれる様子もそのまま見える。IME はブラウザ標準の動きになる |
| 弱い点 | 書体・行の高さ・折り返しが実物とずれやすい。書いている間、下の要素が押し下がらず、確定したときにまとめて動く | `contenteditable` は勝手に `<b>`・`<div>` などを作る。DOM をそのまま信じず、`beforeinput` を止めて、自分で Text・Strong・Em・Link・Br だけに変換する必要がある |
| 確かめること | 文字の形の写し方 | 親の画面から付けたイベントが、sandbox の iframe の中でも動くか（未確認） |

どちらの方式でも、次は守る。

- 確定は `sf.edit.setInline` などの編集操作にし、今と同じく書き出したものを読み直して照合する（editor.md §2）
- IME の変換中（`compositionstart` から `compositionend` まで）は確定しない（R2）
- 書いている間はプレビューを描き直さない（カーソルが消えるため）。描き直すのは、書き終えたとき（Esc、外をクリック、別の部品を選ぶ）
- 書いている間の「元に戻す」は、区切り（変換の確定、一定時間の停止）ごとにまとめる
- Html の箱は編集できる対象にしない。プレビューでも今と同じく中身を出さない

**推奨:** 方式 2 を小さく試作し、イベントが届かないなど根本的な問題が出たら方式 1 にする。どちらも駄目なら、案 A をあきらめて案 B（右の欄を対象のそばに浮かべる形）にする。

**試作の結果（2026-10-29）: 方式 2 で作れた。** 実装は `packages/editor/editor.mjs` の「editing text in place」と `inline-dom.mjs`。

- 確かめたこと（アプリ内のブラウザ、Chromium）
  - 親の画面から付けた `keydown`・`beforeinput`・`input`・`pointerdown` は、sandbox の iframe の中でも届く
  - `beforeinput` の打ち消しと、親からの `execCommand('insertText')` も効く
- 太字は自前で付ける。ブラウザ標準の太字（`formatBold`）は止めて、Ctrl+B で選んだ範囲を `<strong>` で包むか外す。標準の太字を使わないのは、見出しの中で `<span style="font-weight: normal">` を作るなど、出力が予測できないため
  - 外すときは、選んだ範囲を含む太字の全体を外す（一部だけを外すことはまだできない）
- 書き終えたときの読み取り（`inlineFromDom`）は、Strong・Em・Link・Br に当たるタグだけを残し、ほかのタグは外して文字だけにする。ブラウザが作る `<b>`・`<i>` は Strong・Em として読む
- 書き終える操作は Esc、Enter、ほかの場所のクリック、エディタのボタンやソースの欄のクリック。どれも編集 1 回分（元に戻す 1 回分）として保存する
  - 中身が変わっていなければ、ソースは 1 文字も変えない
- Enter は段落の区切りにする
  - 文章（Text）の中で押すと、カーソルの位置で 2 つの文章に分ける。後ろの文章は、大きさと揃えを引き継ぎ、先頭から書き続けられる。分けるのは編集 1 回分
  - 太字の途中で押すと、両側の文章に太字が残る
  - 見出しとボタンの中で押すと、書き終える
  - 空の文章のまま書き終えると、その文章を消す
  - Shift+Enter は行の中の改行（Br）にする
- 書いている途中の Ctrl+Z と Ctrl+Y は、書き終えてからエディタの履歴で戻す・やり直す。つまり、書き始めてからの入力をまとめて 1 回で戻す。ブラウザ標準の元に戻す（`historyUndo`）は止める。自前の太字の付け外しがブラウザの履歴に載らず、戻り方が崩れるため
- 書き終えたあとの Esc は親を選び、いちばん上まで来たら選択を外す（§4.3）
- 貼り付けは文字だけにする（改行は空白に変える）。書いている段落の中での文字のドラッグ（`deleteByDrag`・`insertFromDrop`）は止める
- IME の変換中は、Enter と Esc を IME に任せる（`isComposing` と `compositionstart`〜`end` で判定）
- 書いている途中で再読み込みやタブを閉じたときは、`pagehide` で書いた内容を保存する
- 右の欄の「文字」の入力欄はやめ、プレビューの上で書けることの説明に置き換えた。キーボードだけで文字を直す手段は、§4.3 のキャンバス上での選択を作るまで、ソースだけになる
- ~~案 A との違い: まだ書き始めていない文の上でドラッグすると、部品の移動になる~~ 2026-10-29 に取っ手を作り、案 A のとおりにした。文の上で押すとすぐにカーソルが立ち、そのままドラッグすると文字の範囲選択になる。文の部品は取っ手（⠿）でだけ動く（§3.8）
- アプリ内のブラウザ（Chromium）で、2026-10-29 に操作して確かめたこと
  - クリックして書き、Esc で終える。ソースの差分はその 1 行だけで、字下げは元のまま
  - 太字を含む文に書き足し、Ctrl+B で太字にする
  - 太字の途中で Enter を押して分け、新しい段落の先頭から書き続ける
  - 書いている途中にほかの見出しをクリックすると、前の文を保存して、その見出しを書き始める
  - 書いている途中に、右の欄の「削除」や「揃え」の選択欄、ツールバーの追加のボタンを押すと、1 回のクリックで保存と操作の両方が行われる
  - 書いている途中の Ctrl+Z で、書く前のソースに戻る。続けて Ctrl+Y でやり直せる
  - 何度も Ctrl+Z を押すと、サンプルと 1 文字も違わないソースに戻る
  - 書いている段落の中で、選んだ文字をドラッグしても文字は消えない。ただし、合成した操作が、本当の文字のドラッグとして扱われたかは確かめられていない
  - ソースに書き間違いがある間は、クリックしても書き始めない
  - 書いている間もプレビューをスクロールでき、選択の枠がついてくる
  - スマホ幅のプレビューでも書ける
  - コンソールのエラーはなし
- まだのこと
  - 実際の IME での確認。この環境から IME の変換を起こせないので、判定のコードを書いただけで、動作は確かめていない
  - リンクの追加（Ctrl+K）。既存のリンクは、書いても残る
  - ~~選んだ部品のツールバー（§3.1）~~ 作った（§3.8）
  - キーボードで部品を選ぶこと
  - タッチ操作

### 3.3 保存・公開・履歴（保存 API の形を決める）

利用者から見た規則:

- **保存ボタンは置かない。** 書いたものは自動で下書きとして保存する（入力が止まって約 2 秒後と、部品を離れたとき）。画面上部に「保存しました 14:02」「保存中」「保存できませんでした」を出す
- **下書きと公開を分ける。** 編集しても、公開するまでは公開サイトは変わらない。主な操作は画面右上の「公開」1 つだけにする
- **公開するたびに版を 1 つ残す。** 自動保存は、まとめて間引いた途中経過として残す（10 分ごとなど。仮）
- **戻すのは 1 か所から。** 公開した直後の知らせに「公開を取り消す」を出す。あとからは「履歴」で版を選び、「この版に戻す」を押す（手数 3）

API に与える影響（PHP 側を作る前に決める）:

- 保存の単位はページのソースの文字列（いまのエディタも、状態をソースの文字列だけで持っている）
- 1 ページにつき、下書き（1 つ）、公開中の版への参照、版の一覧を持つ
- 下書きの保存では、元にした版の番号（`baseRevision`）を一緒に送る。番号が合わなければ保存を断り、同時編集として扱う（§6）
- 公開は「下書きのこの版を公開する」という要求にする。公開中に下書きが変わっても、利用者が見て押した内容だけが公開される
- 保存が拒否されたときは、WAF の誤検知（要件 §3.3）か、それ以外かを見分けられる応答にする

### 3.4 パターンと R1 の「部品」

パターン（「お知らせ一覧」「アクセス」「料金表」「3 列の紹介」など、できあがったまとまり）を、R1 の部品（非エンジニアも作れるプラグイン）と同じものにするかどうかで、ソース形式が変わる。

- **展開する方式**: 挿入した時点で、Section・Stack・Heading などの既存の部品に展開する。ソース形式は変わらない。ただし、挿入したあとでパターンの元を直しても、挿入済みのところには反映されない
- **参照する方式**: ソースに `<Part name="access-map" … />` のような参照を残す。元を直すと、使っている全ページが変わる。ソース形式、schema、JS と PHP の両方の書き出し器に「参照」の書き方を足す必要がある

**推奨:** 両方を使い分ける。

- 組み込みのパターンは展開する。挿入したあとは普通の部品として自由に直せる
- サイト共通の部分（ヘッダー、フッター）と、利用者が「選んだ範囲を部品として保存」したものは参照にする
- ヘッダーとフッターは、どのみち全ページで共有しないと運用できない。そのため、参照の書き方は source-format の次の版で決める必要がある

利用者が部品を作る入口は、エディタの中の「選んだ範囲を部品として保存」にする（D4 の非エンジニアのプラグイン作成）。最初の一歩をプラグインの画面ではなく、いつも使っている編集画面に置く。

### 3.5 GUI の言葉は、schema の属性と 1 対 1 で対応させる

ソースにない概念を GUI だけで作ると、双方向（D2）が壊れる。GUI の言葉は、必ず schema の属性 1 つに対応させる。選択欄（`<select>`）より、選べる値が見える切り替えボタンを使う。

| schema | GUI の言葉（案） | 部品 |
|---|---|---|
| `Stack direction` | 並べ方: 縦／横 | アイコン付きの切り替え |
| `Stack align` | 揃え: 左／中央／右／幅いっぱい | アイコン付きの切り替え。日本語のサイトなので「先頭側」ではなく「左」と書く |
| `Stack justify` | 横の配置: 左寄せ／中央／右寄せ／両端に広げる | 同上 |
| `gap`・`padding` | 間隔・余白: なし〜最大（7 段階） | 段階の切り替え。それぞれの幅を図で見せる |
| `Grid columns` | 列の数: 1〜6 | 切り替え。「スマートフォンでは 1 列になります」と書き添える |
| `Heading level` | 1 = ページの題名、2〜4 = 大・中・小見出し | 1 がページ内に 2 つあれば知らせる。5・6 は「その他」の中 |
| `Text size` | 文字の大きさ: 小／中／大 | |
| `Button href`・`Link href` | リンク先 | サイト内のページから選ぶ。外部の URL も入れられる |
| `Button variant` | 目立たせる／控えめ | |
| `Image src`・`alt` | 画像、画像の説明 | 説明には「読み上げや、画像が出ないときに使います」と書き添える。空なら知らせる |
| 属性の指定なし | 「デザインの既定（中）」 | 既定値が実際に何かを見せる |
| `Html` | HTML の埋め込み（管理者だけが編集できます） | |

部品の名前（区画・並び・格子など）は、利用者に直接選ばせる場面を減らす。並びや格子は「パターンを入れ、並べ方を変える」形で出てくるようにする。名前は §7 で、ユーザーテストを通して決める。

### 3.6 ソースの表示

- 既定では隠す。ツールバーの「ソース」（Ctrl+/ など）で、右の欄に出す。出しているかどうかは、利用者ごとに覚えておく
- 出しているあいだは、いまの試作の動き（選んだ部品の範囲に色を付ける、カーソル位置の部品を選ぶ、差分の行数）をそのまま使う
- ソースに書き間違いがあり、GUI の操作を止めているとき（editor.md §1）は、止めている理由と行を平易な言葉で出す。あわせて「最後に読めた内容に戻す」を出す（§6）

### 3.7 スマートフォンでの編集の範囲

推奨: 急ぎの直しと、記事を書くことに絞る。

- できること: 文字と画像の差し替え（T1）、記事を書く（T2）、公開・公開の取り消し・履歴から戻す（T3）、↑↓での並べ替え
- PC に限ること: ドラッグでの配置換え、パターンの挿入と並べ方の変更、ソース
- 画面の作り: 上部はページ名と「公開」だけにする。ツールバーは画面の下（親指の届く位置）に置く。設定は下から出る引き出し（ボトムシート）にする
- 前提として、プレビューを指でスクロールできるようにする（いまはできない。editor.md §6）。タップで選ぶ操作と、指でのスクロールが両立するかを確かめる

### 3.8 ツールバー・挿入点・保存の試作の結果（2026-10-29）

実装は `packages/editor/` の `editor.mjs`（block toolbar、insertion points、saving, publishing, history の各節）と `store.mjs`（テスト 7 件）。

作ったもの:

- 選んだ部品のツールバー。部品のすぐ上に出し、上に余白がなければ部品の上端の内側に出す
  - 並び: 取っ手 ⠿ ／ 道筋 ／ ↑ ↓ ／ ＋（この後ろに足す）・複製・削除
  - 道筋の各段を押すと、その外側の部品を選ぶ。右の欄の「親を選ぶ」「前へ」「後ろへ」「削除」はやめ、ツールバーに移した
  - 道筋が 5 段以上になると、最初の 1 段と最後の 2 段だけを出し、あいだは「…」にする
  - キー: Alt+↑↓（移動）、Ctrl+D（複製）、Delete（削除）
  - 削除は確認なしで行い、下の帯に「◯◯を削除しました」と「元に戻す」を出す
- 文の上で押すとすぐ書き始め、ドラッグは文字の範囲選択にした（U1 の案 A どおり）。画像と箱は、今までどおり押してそのままドラッグで動かせる
- 部品のあいだの挿入点
  - 部品と部品の隙間（線から 12px 以内）にマウスを置くと、線と ＋ が出る。中身のない箱では、箱の上にいるあいだずっと出る
  - 線の位置は、ドラッグの落とし先と同じ計算（`dropTarget`）で決める。追加とドラッグで、入る場所の考え方が食い違わない
  - ＋ を押すと一覧が出る。並びは「見出し・文章・画像・ボタン」、区切り線、「区画・並び・格子」
  - 見出しと文章は、入れた直後に仮の文字を選んだ状態で書き始めるので、そのまま打てば置き換わる
  - 上部の「＋区画」などの並びはやめた
- ソースは既定で隠す（U2）。上部の「ソース」か Ctrl+/ で出し、出したかどうかは localStorage に覚える。属性名（`level` など）と部品名（`<Heading>`）、選択肢の英語の値は、ソースを出しているときだけ添える
- 自動保存・公開・履歴（§3.3）
  - 変更の約 1.5 秒後と、ページを離れるとき（`pagehide`）に下書きを保存する。上部に「未保存の変更があります」「保存中…」「保存しました 04:29」「保存できませんでした。再試行しています」を出す
  - 「公開」は塗りのボタン 1 つだけ。公開中と同じ内容のときは「公開済み」として押せなくする
  - 公開の直後、下の帯に「公開を取り消す」を出す。押すと、公開中のページはその前の版（なければ非公開）に戻る
  - 「履歴」を押すと、公開した版と自動保存の版（10 分ごと、新しい 30 件まで）が並ぶ。「この版に戻す」で下書きに戻す。戻すのはエディタの操作 1 回分なので、元に戻すで取り消せる
  - 別のタブが先に保存していたら（`baseRevision` の不一致）、保存を止めて「そちらを読み込む」「こちらで上書きする」の 2 択を出す
  - 保存の中身は当面 localStorage。`store.mjs` のメソッド（`load`・`saveDraft`・`publish`・`undoPublish`・`listVersions`・`getVersion`）を、そのままサーバーの API に置き換える前提
  - 前の試作が `wge-editor-source` に残した内容があれば、最初の下書きとして引き継ぐ

アプリ内のブラウザ（Chromium、1440×900）で操作して数えた手数（文字入力を除く）:

| タスク | 見込み（§3.1・§4.2） | 実測 | ソースの差分 |
|---|---|---|---|
| T1 文の差し替え（営業時間に書き足す） | 1＋入力 | クリック 1 ＋入力。終えるのは Esc か、ほかの場所のクリック | 1 行 |
| T4 見出しを足す | 2＋入力 | ＋ 1、「見出し」1 ＋入力 | 1 行。字下げは周りの行に合った |
| T1 文の一部を太字にする | — | 文の上でドラッグ（書き始めと範囲選択を兼ねる）、Ctrl+B | 1 行 |
| 並べ替え（カードを隣のカードの後ろへ） | 1〜2 | 画像をクリック、道筋の「並び」、取っ手でドラッグの 3 | 5 行の移動だけ |
| 複製・Alt+↑・削除 | — | 各 1 | +5 行 ／ −5 +5 行 ／ −5 行 |
| T3 公開 | 2（確認つき） | 1。確認は出さず、直後に取り消しを出す | — |
| T3 公開を取り消す | — | 1（公開の直後の帯） | — |
| T3 前の版に戻す | 3 | 「履歴」1、「この版に戻す」1 の 2 ＋公開 1 | 版の内容に置き換わる |

ほかに確かめたこと:

- 文の上のドラッグは文字の範囲選択になり、ソースは変わらない
- 知らせの「元に戻す」、上部の「元に戻す」で、削除・複製・移動の前のソースに 1 文字も違わず戻る
- 自動保存の約 2 秒後に、保存先（localStorage）の下書きが画面のソースと一致する
- 公開後に書くと、ボタンが「公開済み」から「公開」に戻る。公開中の版は書き換わらない
- 別のタブの保存を、保存先を直接書き換えて再現した。衝突の 2 択が出て、「そちらを読み込む」で相手の内容になり、「こちらで上書きする」で自分の内容が保存された
- 変更の 0.4 秒後（自動保存の前）に再読み込みしても、変更は残っていた
- 375×812 でも、ツールバーは表示域の中に収まる（幅 341px ／ 349px）。横のはみ出しはない
- コンソールのエラーはなし

確かめていないこと・決めたこと:

- 取っ手でカードを隣のカードの「中ほど」に落とすと、そのカードの中に入る。これは既存のドロップの規則（箱の端 24px 以内なら隣、それより内側なら中）どおりで、落とす前に「並び → 並びの 1 番目」と表示される。カードの中にカードを入れることはまれなので、規則を見直す余地がある
- 公開の確認の画面（§5 の「内容の確認で公開」）は作らなかった。取り消しがすぐ出せるので、確認より手数を減らすほうを選んだ。ユーザーテストで確かめる
- 公開中のページを見る手段がまだない（公開先がないため）
- スマートフォン幅では上部が 3 段に折り返し、高さ 126px になる。§3.7 の「上部はページ名と公開だけ、ツールバーは画面の下」はまだ作っていない
- タッチでの取っ手のドラッグ、挿入点（ホバーがないので出ない）は未対応・未確認
- 衝突は、保存しようとしたときに初めて分かる。開いた時点での「◯◯さんが編集中です」（§6）はサーバーが要る

## 5. 初回から公開まで（R2 の 30 分の物差し）

```
インストーラーの完了 → ログイン（passkey の登録） → ホーム「はじめにすること」
  1. サイトの名前と種類（お店／会社／個人／ブログ）を入れる   入力 1＋選択 1＋次へ 1
     → 種類に合うパターンでトップページを作り、サイト名を入れておく
  2. トップページを整える（T1 を繰り返す。写真の差し替え）     1 か所につき 1〜2＋入力
  3. 公開する                                                「公開」→ 内容の確認で「公開」 2
     → 「公開しました」＋「サイトを見る」＋「次は最初の記事を書きましょう」
  4. 最初の記事を書く                                        「記事を書く」1 → 題名と本文を入力
  5. 記事を公開する                                          2
```

文字入力を除いた手数は、整える箇所を 5 か所として約 20。30 分の大半は、写真の用意と文章を考える時間になる見込み（未計測）。ほかの入口として、WordPress からの移行（D3）を「はじめにすること」の 1 の代わりに選べるようにする。

記事のエディタは、ページのエディタと同じキャンバスを使う。違いは次のとおり。

- 本文の部品の一覧は、文章・見出し・画像・ボタン・パターン（一部）に絞る。記事のページの枠（ヘッダーや横の欄）はデザインが決める
- 何も選んでいないとき、右の欄は記事の設定にする（カテゴリ、タグ、アイキャッチ、公開日時、URL、説明文）
- 公開日時を未来にしたときは、予約投稿が cron で動くことを踏まえて「◯時以降、最初の定期処理で公開されます」と書く。cron が止まっているときは、その旨も出す（要件 §3.3）

## 6. 状態の一覧

| 状態 | 見せ方（案） |
|---|---|
| 空のページ | 「パターンから始める」と「白紙から書く」の 2 つ |
| 保存中・保存した | 上部の小さな文字。位置は動かさない |

| 公開中・公開した | 「公開しました。サーバーの仕組みで、数分間は前の表示が見えることがあります」（要件 §3.3。エックスサーバーは 2 分、シンは 5 分）。あわせて「公開を取り消す」を出す |

## 7. あとから直せる表面

- 部品の呼び名（「区画」→「セクション」か「まとまり」か、など）は、ユーザーテストで決める
- 色: ブランドの指定がないので、強調色は OS の標準に近い青 1 色にする。塗りのボタンは「公開」だけ
- 押し領域: PC では 24px 以上。指で触る画面では 44px 以上
- 「サンプルに戻す」は製品の画面から外す（開発用のメニューに移す）
- 属性名（`level` など）と部品名（`<Heading>`）は、ソースを出しているときだけ添える
- ツールバーのアイコンは、文字かツールチップを必ず付ける
