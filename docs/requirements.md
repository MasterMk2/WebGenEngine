## 0. この文書の読み方

- **要件**は「何を満たすべきか」、**方針案**は「それをどう満たすか」の推奨で、まだ確定していない。
- `[仮]` を付けた数値は議論のための置き値。実態に合わせて直す。
- 決定済みの事項は §7 の D 番号、未決の事項は Q 番号で参照する。
- 「調査メモ」は `docs/research/rental-servers-2026-10.md`（国内レンタルサーバーの標準環境調査）を指す。

## 1. 目的と「上位互換」の定義

WordPress が担ってきた「専門知識のない人が、自分でサイトを作って運用し続けられる」役割を引き継ぐ。そのうえで、WordPress の次の弱点を解消する。

- 脆弱性の大半がプラグイン由来で、利用者に防ぎようがない
- GUI（ブロックエディタやページビルダー）で作ったページのソースが読めない
- 安全に運用し続けるには、結局専門知識が要る

「上位互換」の定義:

1. WordPress で一般的なサイト（ブログ、企業サイト、小規模メディア）でできることは、すべてできる
2. §2 の 7 要件で WordPress を明確に上回る
3. WordPress から次のものを取り込める（D3）
   - コンテンツ: 記事、固定ページ、画像、カテゴリ、タグ、ユーザー、URL
   - テーマ: 見た目を変換して取り込む（§3.5）
   - 主要プラグインのデータ: カスタムフィールド（ACF など）、SEO 設定（Yoast SEO など）、フォーム定義（Contact Form 7 など）
4. WordPress の PHP プラグインは動かさない
   - 理由: 任意の PHP プラグインを本体と同じ権限で動かすことが、WordPress のセキュリティ問題の根本にある。要件 R6 と両立しない
5. WordPress と同じく、国内のレンタルサーバーで動く（D1）

## 2. 要件と受け入れ基準

### R1. プラグインが容易に作れる（非エンジニアを含む。D4）

非エンジニア向け:

- 既存のブロックを組み合わせて「部品」にし、編集できる項目を指定して、プラグインとして書き出せる。プログラムを書かずに 15 分以内 `[仮]`
- 独自のデータ型（例: 「物件」「メニュー」）と、その入力項目を GUI で定義できる
- 「〜したら〜する」という処理（例: フォーム送信 → メール送信と一覧への保存）を画面上で組み立てられる

開発者向け:

- 雛形生成のコマンド 1 つで、動く「Hello World」ブロックプラグインができる。そこから 10 分以内 `[仮]` に表示を変えて確かめられる
- 最小のブロックプラグインは、設定ファイルと表示テンプレートの 2 ファイル、合計 30 行程度 `[仮]` で書ける
- 型定義、保存すると即時反映されるローカル開発サーバー、テスト用の仕組みを公式に用意する
- プラグインの設定画面は、項目の定義（スキーマ）を書けば自動生成される。管理画面の UI を手書きしなくてよい

共通:

- 非エンジニアが GUI で作ったプラグインと、開発者がテキストで書いたプラグインは、同じ形式になる
- GUI で作ったプラグインも読めるソースとして取り出せ、手で直して GUI に戻せる（R4 と同じ双方向）

### R2. 専門知識のない人でも容易に扱える

- 初めて触る人が説明書なしで、初回起動から 30 分以内 `[仮]` にトップページと記事 1 件を公開できる（5 人中 4 人以上 `[仮]` のユーザーテストで確認）
- 画面に専門用語（HTML、CSS、データベース、DNS など）を出さない。出す場合は平易な説明を添える
- どの操作も取り消せる。公開済みの内容も、過去の版へワンクリックで戻せる
- PC で作ったレイアウトが、追加作業なしでスマートフォンでも崩れない
- 日本語入力（IME の変換中）でエディタが誤動作しない

### R3. GUI 主体で操作できる

- 日常の運用が GUI だけで完結する: 記事の作成・編集・公開、レイアウト変更、画像の追加、プラグインの作成・導入・設定、ユーザー追加、バックアップと復元、更新
- FTP などのファイル操作が要るのは初回の設置だけにする（R7）

### R4. GUI で配置したものでも、可読性の高いソースにできる（双方向。D2）

- 生成ソースに絶対座標（`top` / `left` の px 指定）や、根拠のない数値（`13px` など）が出てこない
  - 位置関係は「中央揃え」「左揃え」「均等配置」など意図を表す指定で書かれる
  - 余白や大きさはデザイントークン（間隔の段階など）で書かれる
- 出力は決定的: 同じ内容なら常に同じソースになる（属性の順序や整形も固定）
- GUI で 1 か所変えると、ソースの差分も 1 か所（数行）に収まる。Git で履歴を管理できる
- HTML/CSS の基礎知識がある人が、生成ソースを読んでページの構造を説明できる
- 手で書き換えたソースを GUI で開いて保存しても、触っていない部分に差分が出ない
- GUI で表せない書き方は、該当する行を示してエラーにするか、GUI では中身を編集しない箱（カスタム HTML ブロック）として扱う
- サイトのソース一式を取り出し、手で直して戻せる（初期版は zip。Git 連携は後の版）

### R5. GUI でずれた配置を容易に修正できる

- ドラッグ中に揃え先（中央線、他の要素の端、等間隔）をガイド表示し、吸着させる
- 「ずれ」を検出して一覧にし、1 クリックで直せる。検出対象 `[仮]`:

  | ずれの種類 | 判定 | 直し方 |
  |---|---|---|
  | 中央からのずれ | 中央から 8px 以内 | 中央揃えにする |
  | 端のずれ | 他の要素の端から 4px 以内 | 端揃えにする |
  | 間隔の不揃い | 隣り合う間隔の差が 25% 以内 | 均等配置にする |
  | トークン外の値 | 余白・大きさがトークンにない | 最も近いトークンにする |

- 数値を微調整して直すのではなく、意図の指定（「中央揃え」など）に置き換えて直す。これで R4 も同時に満たす
- ページ全体をまとめて整えることもでき、適用前に変更内容をプレビューで確かめられる

### R6. 専門知識なしで堅牢に運用できる

- 初期設定のままで安全。安全性を下げる設定は通常の画面に出さない
- 公開ページは静的ファイルで配信し、閲覧者のアクセスではプログラムを動かさない（§3.3）
- GUI から導入できるプラグインは宣言型だけ。宣言した権限の外には構造上アクセスできない（§3.2）
- 本体とプラグインは署名付きで自動更新し、更新後に異常があれば自動で元に戻す
- 管理画面のログインは passkey または 2 段階認証を既定にする。総当たり攻撃は自動で遮断する
- 自動バックアップを既定で有効にし、GUI からワンクリックで復元できる
- 安全性の状態を平易な言葉で示す画面を設ける
  - 例: 「更新が 3 日止まっています」「PHP のバージョンが古くなっています」「HTTPS が無効です」
- 管理画面に、任意のコードを編集・実行する機能（WordPress のテーマファイルエディタに当たるもの）を置かない
- 本体ファイルの改ざんを検知する。配布時のハッシュ一覧と照合し、見覚えのない `.php` ファイルが現れたら警告して隔離する。結果は安全性の状態の画面に出す
- PHP が返す応答（管理画面、API、フォームの入口、インストーラー、診断）には、すべて `Cache-Control: no-store, private` を付ける。レンタルサーバーの前段キャッシュに残り、他人に表示されるのを防ぐ（調査メモ §3）
- cron が動いていないことを検知し、安全性の状態の画面で警告する。cron が止まると、自動更新、自動バックアップ、予約投稿が止まるため（§3.3）

### R7. 容易にサーバーに配置できる（D1）

- 主な配置先は国内レンタルサーバーの標準環境（PHP）。SSH やコマンド操作を前提にしない
- 対応するサーバーは D6、最低 PHP バージョンは 8.3（D7）
- FTP でファイルを 1 つアップロードし、ブラウザで開いて画面の指示に従うだけで動く。所要 10 分以内 `[仮]`
  - インストーラーが本体を取得して展開する。サーバーから外への HTTPS 通信やアーカイブの展開が使えない環境では、本体一式を FTP でアップロードする手順に切り替える
- インストーラーは設置先の環境を診断し、足りないものと対処を平易な言葉で示す（診断項目は調査メモ §5）
- インストーラーは、設置が終わったら自分を削除するか無効にする
- データベースの作成を必須にしない（D13）。SQLite が使えない環境（ConoHa は公式に記載がない）では、レンタルサーバーの管理画面でデータベースを作る手順を案内する。この場合は所要 10 分の目標を外れうる
- データファイル（SQLite など）、バックアップ、設定を置くディレクトリは次のとおりにする
  - 公開ディレクトリの外に書けるサーバーでは、外に置く
  - 置き場所にかかわらず、推測されにくい名前にし、アクセス拒否の設定を置く。公開ディレクトリの外が、別のドメインの公開領域に当たっているサーバーがあるため（ロリポップなど）
  - 公開ディレクトリの中に置く場合は、インストーラーの画面（利用者のブラウザ）から HTTP での取得を実際に試し、拒否されることを確かめてから先へ進む。URL には一意のクエリを付けてキャッシュを避ける。サーバー自身からのアクセスで試さないのは、外への通信が使えるかが未確認で、閲覧者と同じ経路を通る保証もないため
- cron を 1 件、5 分間隔で登録することを、設置の必須手順にする（§3.3）
  - 登録するコマンドは、版付きの PHP のパスで画面に表示する
  - 最初の動作記録を確かめるまで「設置完了」にしない。確認待ちの最大 10 分程度は、所要 10 分の目標とは別に数える `[仮]`
  - 登録できない間は、「設置が終わっていない」状態として画面に出し続ける
- HTTPS が無効なら、レンタルサーバーの管理画面で有効にする手順を案内する。HTTPS でない間は管理画面にログインさせない `[仮]`
- 配布物と書き出しのファイル数を少なく保つ。ファイル数に上限のあるサーバーがある（mixhost のライトは 100,000）
- 移設やバックアップが、決まったフォルダのコピーだけで済む
- 副次的に VPS や Docker でも動く（PHP なので、そのまま動かせる）

## 3. 要件どうしの関係と設計方針案

7 要件は独立していない。両立させる設計の要点は次の 5 つ。

### 3.1 R4（可読ソース）と R5（ずれ補正）は、同じ設計判断で両方解ける

分岐点は、レイアウトの正本データを**座標**で持つか、**構造（並べ方の指定）**で持つか。

Wix のような自由配置（座標で持つ）を採ると、次の問題が同時に起きる。

- ソースが座標の羅列になり、読めない（R4 が崩れる）
- 数 px のずれが、そのまま座標として残り続ける（R5 が崩れる）
- 画面幅が変わると崩れる（R2 のスマートフォン対応が崩れる）

**方針案:** 正本は構造ツリー（縦・横の並び、グリッド、揃え方、間隔トークン）にする。GUI 上のドラッグは自由に見せつつ、離した時点で「意図」に変換して保存する。

- 例: 中心から 3px ずれた位置に置いた → 「中央揃え」として保存する
- 意図を判断できない場合は候補を示し、利用者に選んでもらう

こうすると、ずれの多くはそもそも保存されない。残ったずれも「トークン外の値」として機械的に検出できる。この「位置関係から意図を推定する」機能は、WordPress テーマの変換（§3.5）にも使い回せる。

生成ソースのイメージ（記法は例。形式は未定）:

```html
<Section padding="lg">
  <Stack align="center" gap="md">
    <Heading level="1">ようこそ</Heading>
    <Button href="/contact">お問い合わせ</Button>
  </Stack>
</Section>
```

座標で持った場合の典型的な出力（避けたいもの）:

```html
<div style="position:absolute; left:347px; top:122px; width:613px">
  <h1 style="margin-left:13px">ようこそ</h1>
</div>
```

### 3.2 R1（作りやすさ）と R6（堅牢性）: PHP では隔離実行ができない → プラグインを「コード」ではなく「宣言」にする

WordPress では、プラグインが本体と同じ権限で何でもできる。これが脆弱性の大半を生む。

一般的な解決策は、プラグインを隔離環境（サンドボックス）で動かすこと。Cloudflare の EmDash（2026 年 4 月公開。報道ベースで、一次資料は未確認）もこの方式だが、隔離実行を Cloudflare の有料機能に頼っていると報じられている。そしてレンタルサーバーの PHP には、任意のコードを安全に隔離して動かす仕組みがない。

**方針案:** プラグインを PHP コードではなく、宣言（データ）として書かせる。本体がそれを解釈して実行するので、宣言された権限の外には構造上出られない。

- プラグインの中身は次の組み合わせ
  - 部品（ブロックの組み合わせと、編集できる項目）
  - データ型と入力項目
  - ルール（きっかけ → 条件 → 動作）
  - 表示テンプレート
- ルールの「動作」は、本体が用意したものから選ぶ（メール送信、記事の作成、指定したドメインへの HTTP 送信など）。動作ごとに権限が要る
- 導入時に、必要な権限を平易な日本語で示して承認してもらう（スマートフォンアプリの権限確認と同じ形）
- 条件や計算は安全な式言語で書く。処理回数と時間に上限を付け、無限ループにならないようにする

この形式は、非エンジニア向けのノーコード作成（D4）と相性が良い。ノーコード作成は「この形式を GUI で組み立てる機能」になり、開発者は同じ形式をテキストで書く。R4 と同じく、同じものを GUI とソースの両方から扱う。

ブラウザで動く JavaScript は、ブラウザ自体が隔離するので許可する。

- 管理画面に追加する UI: 隔離した iframe の中で動かし、本体とは決まった API でだけやり取りする
- 公開サイトで動くスクリプト: 「閲覧者のブラウザでスクリプトを動かす」という権限として明示する。読み込み元はプラグイン内のファイルに限る（CSP で強制）

拡張の段階:

| 段階 | 作れる人 | できること | 実行のされ方 |
|---|---|---|---|
| 1. 部品・見た目 | 非エンジニア、開発者 | ブロックの組み合わせ、テンプレート、スタイル | 静的ファイルに書き出すだけ |
| 2. データ型 | 非エンジニア、開発者 | 独自の投稿タイプと入力項目 | 本体が解釈 |
| 3. ルール | 非エンジニア、開発者 | きっかけ → 条件 → 動作 | 本体が解釈（宣言した権限の範囲のみ） |
| 4. ブラウザ側スクリプト | 開発者 | 閲覧者側の動き、管理画面の独自 UI | ブラウザ内（iframe と CSP で隔離） |

**限界:** 宣言では書けない処理がある（決済、複雑な外部連携、重い計算）。対応案は次のとおり。

- 本体側に公式モジュールとして用意する（決済など）
- 外部サービスへの HTTP 連携で実現する（処理はサイトの外で動く）
- PHP で書く拡張は、公式の署名付き拡張だけを認める（D12）

### 3.3 R6（堅牢）と R7（容易な配置）: 同じレンタルサーバー上でも、公開側は静的にできる

**方針案:** PHP は管理画面と最小限の動的処理だけを受け持ち、公開ページは静的ファイルとして書き出す。

- 閲覧者がページを開いても PHP は動かない（WordPress は全ページで PHP とデータベースが動く）
- 動的処理（フォーム送信、検索、コメント）には、それぞれ小さな専用の入口だけを用意する
- 書き出し先に置くのは HTML、CSS、JS、画像だけにし、`.php` へのアクセスを `.htaccess` の `Require all denied` で拒否する。CGI・FastCGI・LSAPI では `php_flag engine off` が効かず、エックスサーバーでは `php_flag` 自体がエラーになるため。設定を書いて終わりにせず、インストーラーと安全性の点検で、利用者のブラウザから実際に拒否されることを確かめる
- 2026 年 10 月には PHP 本体の重大な脆弱性で、各社が緊急対応をした（調査メモ §4）。公開ページが PHP を通らない構成なら、こうした事態でも公開側への影響を小さくできる
- 管理画面は別のパスに置き、ログイン試行の制限などを自動で設定する

レンタルサーバーの制約への対応（根拠は調査メモ）:

- 実行時間とメモリに上限がある（既定値はどの社も公開していない）
  - 書き出しは、変更のあったページとその影響を受けるページだけにする。量が多いときは複数回に分けて処理する
  - 上限はインストーラーで実測し、処理の分け方を合わせる
- `.htaccess` の書き方に各社の制約がある → 生成する `.htaccess` は次の規則で書く
  - ASCII 文字だけで、Apache 2.4 の書き方（`Require all denied` など）にする
  - `php_value` / `php_flag` は使わない。PHP の設定は、スクリプト内の `ini_set` で済む範囲にとどめる
  - `Options` は `-Indexes` だけにする（さくらは `All` と `FollowSymLinks` を指定できない）
  - ファイルを丸ごと上書きせず、目印で囲んだ区画だけを書き換える（エックスサーバーと ConoHa は、サーバー側が自動で行を足す）
- 前段にキャッシュがある
  - PHP の応答にはすべて `Cache-Control: no-store, private` を付ける（R6）
  - 公開ページは、公開や差し戻しの直後に古い表示が数分残る（エックスサーバー 2 分、シン 5 分）。公開の画面でそのことを知らせる
- 常駐プロセスを置けない → 予約投稿、自動更新、自動バックアップは cron で動かす
  - cron は 1 件、5 分間隔にする。最も制限の強いロリポップのライト（5 件まで、最短 5 分）に収まる
  - 登録するコマンドは、版付きの PHP のパス（例: `/usr/bin/php8.3`）で画面に表示する。エックスサーバーではコマンドラインの PHP の既定が 8.0 で、Web 側と違うため
  - cron が動いたことを毎回記録し、止まっていれば安全性の状態の画面で警告する。さくらは予告なく cron を解除することがあり、ロリポップは PHP の版を変えると登録し直しが要る
  - cron の登録は設置の必須手順にする（R7）。対象プランはすべて cron が使える。cron がない状態は、一時的に機能が落ちた状態として扱う
  - 必須にする理由: 設置後に管理画面を開かない利用者もいる。cron がないと自動更新と自動バックアップが止まり、警告のメール通知も送れない。R6 が守ろうとする利用者ほど影響を受ける
  - cron が止まっている間は、管理画面を開いたときにまとめて処理する。予約投稿は次に管理画面を開くまで公開されないので、予約の画面でそのことを明示する
  - 採らなかった案: 公開ページから閲覧のたびに PHP を呼んで処理を進める方式。予約時刻からの遅れは小さくなるが、公開側で PHP を動かさない原則（R6）に反し、閲覧のたびに PHP の負荷もかかる。外部の cron サービスから呼ぶ方式も、外部への依存と公開された入口が増えるので採らない
  - 将来の候補: エックスサーバーとシンは cron を登録する API を公開している。利用者の許可を得て自動で登録できれば、手順を省ける
- サーバーの WAF が、管理画面からの保存を誤って止める可能性がある（mixhost は mod_security が標準で有効。誤検知は推論）→ 保存が拒否されたら、原因と対処を平易な言葉で示す

### 3.4 R2・R3（非専門家、GUI 主体）と R4（双方向編集。D2）

- ソースの書き方を、GUI が理解できる範囲に制限する。制限は読みやすさとは相性が良いが、上級者の自由度は下がる。逃げ道はカスタム HTML ブロック
- ソースの読み書き（パーサー）が、ブラウザのエディタ（JavaScript）とサーバー（PHP）の 2 か所に要る。両者の解釈が食い違うと双方向が壊れるので、共通のテストデータで一致を常に確かめる
- 手書きのソースには任意の HTML やスクリプトも書けてしまう。生の HTML を書けるのは管理者だけにし、それ以外の役割では無害化する

### 3.5 WordPress テーマの変換（D3）

PHP で書かれた従来型テーマには任意の PHP 処理が含まれるので、コードを直接変換するのは一般には不可能。

**方針案:** コードではなく見た目を変換する。

- ブロックテーマ（`theme.json` とブロック形式のテンプレート）: 構造がはっきりしているので直接変換する。`theme.json` の色、文字、余白はデザイントークンに対応づける
- 従来型テーマ: 表示結果（HTML と CSS）を取り込み、要素の位置関係から「中央揃え」「均等配置」などの意図を推定して構造に変換する（§3.1 の推定機能を使う）
- 移行元の WordPress に入れる「移行用プラグイン」を用意し、コンテンツ、テーマ情報、各ページの表示結果、主要プラグインのデータをまとめて書き出す
- 移行元の WordPress が動いていなくても取り込めるようにする。入力は次の 3 経路
  - 移行用プラグインの書き出し（WordPress が動いている場合。最も情報が多い）
  - WXR ファイル（WordPress 標準の書き出し形式）
  - データベースのダンプとファイル一式（WordPress が起動しない場合）。表示結果が取れないので、テーマはテンプレートと CSS から推定する

記事本文の変換も、テーマと同じ問題を抱える。WordPress の本文には次のものが混在する。

- ブロックエディタのマークアップ → 対応するブロックに変換する
- ショートコード（プラグインごとの独自記法） → 主要なものは対応する部品に変換し、残りは報告する
- ページビルダー（Elementor など）のデータ → 実質的にテーマ変換と同じ問題。表示結果から構造を推定する

受け入れ基準 `[仮]`:

- v1: WordPress の標準テーマ（Twenty Twenty-Five など）とブロックテーマは、主要ページ（トップ、記事、固定ページ、一覧）の見た目が目視で同等になる
- v1: 従来型テーマは試験提供とする。変換はできるが、見た目が同等になることは保証しない。試験提供であることを画面上で明示する（D5）
- v2: 国内で利用の多いテーマ上位 N 件 `[要調査]` も、主要ページの見た目が目視で同等になる。これらの多くは従来型テーマや有料テーマと見込まれる（未検証）
- 変換できなかった箇所（テーマ、ショートコード、ページビルダー）は必ず一覧で報告し、どこを手で直せばよいかがわかる

留意: 変換後のテーマで元テーマのライセンス（多くは GPL、有料テーマは各社の規約）をどう扱うかは確認が要る。

## 5. 技術方針の候補（未確定）

D1（国内レンタルサーバー）を受けた第一候補:

- サーバー側: PHP 8.3 以上（D7）。8.4 以降にしかない構文や関数は使わず、8.3 / 8.4 / 8.5 で動作を確かめる。依存ライブラリは同梱して配布し、サーバー上でのビルドを要らなくする
- エディタ: ブラウザで動く JavaScript アプリ。ビルド済みのファイルを同梱し、サーバーに Node.js を求めない
- 正本データ: 構造ツリー。人が読める形式で保存し、取り出しと戻しができる。ソースの形式と、JS・PHP 両方のパーサーの試作は `docs/design/source-format.md`
- データ保存: SQLite を既定にし、MySQL/MariaDB も選べる（D13）
  - pdo_sqlite がない、または SQLite が古すぎる環境では、インストーラーが MySQL/MariaDB に切り替える
  - スキーマは SQLite 3.26 で動く範囲にする（`RETURNING`、`DROP COLUMN`、生成列、`STRICT` テーブルを使わない）。エックスサーバーの新しいサーバーのライブラリが 3.26 系のため
- プラグイン: 宣言型（§3.2）。式言語は既存の安全な仕様を採るか自作するか未定
- 自動更新: 署名を検証してから差し替える。旧版を残し、異常時は自動で戻す
  - sodium 拡張がない環境に備えて、署名検証の純 PHP 実装を同梱する（WordPress も同じ方式）
  - 更新パッケージの展開は、zip 拡張がなくても動く方式にする
- 画像: GD が対応する形式を実測する。WebP/AVIF を作れない環境では、管理画面（ブラウザ）側で変換してからアップロードする案を検討する
- 公開: 静的ファイルの書き出しと、最小限の PHP の入口

## 6. 初期版の範囲（段階計画案）

D1、D3、D4 で負担の大きい選択肢を採ったので、初期版の範囲を絞る必要がある。

| 段階 | 主な内容 |
|---|---|
| 初期版（v1） | 構造ベースのエディタ、双方向ソース、ずれ補正、記事・固定ページ・メディア・ユーザー、静的書き出し、レンタルサーバー向けインストーラー、自動更新とバックアップ、宣言型プラグイン（部品、データ型、簡単なルール）とノーコード作成、WordPress のコンテンツ移行、ブロックテーマと標準テーマの変換、従来型テーマの変換（試験提供）、お問い合わせフォーム |
| v2 | 従来型テーマの変換（国内上位 N 件で見た目が同等）、ルールの拡充、プラグインの配布の場、サイト内検索、Git 連携 |
| v3 以降 | 会員制、EC、サイトの多言語化、AI エージェントからの操作 |

従来型テーマの変換は、v1 で試験提供し、v2 で国内上位 N 件の基準を満たす（D5）。§3.1 の意図推定は v1 のずれ補正のために作るので、v1 から v2 で増える作業は主に精度の調整と、上位 N 件での検証になる。

## 8. リスク

| リスク | 内容 | 対策案 |
|---|---|---|
| 宣言型プラグインの表現力不足 | 書けない処理が多いとプラグインが増えず、WordPress から移ってもらえない | WordPress の人気プラグイン上位が宣言で書けるかを先に検証する。書けないものは公式モジュールで補う |
| パーサーの食い違い | JS と PHP で解釈がずれると、双方向編集が壊れる | 共通のテストデータで両方を常に検証する |
| テーマ変換の再現度 | 期待した見た目にならず、移行をあきらめられる | 対象と基準を明示し、変換できなかった箇所を必ず報告する |
| 共有サーバーの制限 | 実行時間、メモリ、使える拡張の制限で、大きなサイトの書き出しや画像処理が止まる | 差分の書き出しと分割処理。使える拡張を検出して処理を切り替える |
| 本体の脆弱性 | PHP では本体の中で権限を分けられないので、本体に穴があると全権限を取られる | 公開側を静的にして、攻撃される面を管理画面と小さな入口に絞る。ログインを強くする。署名付き自動更新ですぐ直す |
| 自動更新と書き込み権限の衝突 | 自動更新のために PHP が自分のコードを書き換えられる必要がある。侵入されると不正な PHP ファイル（ウェブシェル）を置かれうる。WordPress と同じ構造 | 署名を検証してから差し替える。本体ファイルのハッシュ照合で、改ざんと未知の `.php` を検知して隔離する |
| データファイルの露出 | SQLite のファイルやバックアップが公開領域にあると、パスワードのハッシュごとダウンロードされうる。ロリポップでは公開ディレクトリの外も、別のドメインの公開領域になりうる | 置き場所にかかわらず、推測されにくい名前とアクセス拒否の設定を使う。公開ディレクトリの中に置く場合は、取得できないことを実際に確かめる（R7） |
| PHP 8.3 のサポート終了 | 最低 PHP を 8.3 にした（D7）。8.3 のセキュリティ修正は 2027-12-31 で終わる。さくらは 8.4 を約 2 年追加していない。8.4 が来ないまま期限を過ぎると、安全性の画面が警告し続けるのに、利用者には直す手段がない | 2027 年中にさくらの対応を確かめ、最低バージョンを上げるか、さくらの扱いを見直す |
| 実機で確かめられない | PHP から SQLite を使えるか、公開ディレクトリの外に書けるかなど、公式情報で埋まらない項目が多い。ロリポップと ConoHa は 2026-10-24 から新規申し込みを止めていて、検証用アカウントを取れない | 診断スクリプトを先に作り、既存アカウントで各社を確かめる |
| WAF の誤検知 | 管理画面からの保存（HTML やスクリプトを含む）が、サーバーの WAF に止められうる（推論） | 拒否を検知して対処を案内する。各社の実機で保存の流れを試す |
| 範囲の大きさ | 初期版が大きく、完成が遠のく | §6 の段階計画で初期版を絞る |
